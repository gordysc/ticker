Ticker · build guide

The game loop, in six stages

Ticker is a small 2D platformer in C++20 and raylib. The git history builds its game loop one step at a time, from a naive variable timestep to a fixed timestep with interpolation, replays and time controls. This page explains each stage, the problem it shows and the commit that fixes it.

Read the history

Each stage ends with a tag. Check out a tag to see the code and play the game as it was at the end of that stage.

git checkout stage-1-variable-timestep    # the naive loop
git checkout stage-3-accumulator          # the fixed timestep
git checkout main                         # the finished game

To see what one stage changed, compare two tags:

git diff stage-2-fixed-step-per-frame stage-3-accumulator
git diff --stat stage-3-accumulator stage-4-interpolation

Every commit builds with no warnings. From the first test commit on, every commit also passes its tests. You can check out any commit, not only the tags.

The written guide in docs/game-loop.md has the same content as this page in plain text, with a "Try it" list for each stage. The source files have teaching comments on every class, function and member.

The core design

One decision makes every later stage possible. The simulation and the program around it are separate.

  • Step(world, level, input, dt) in src/world.cpp is the whole game logic. It reads no clock and no keyboard. The caller gives it the input and the time to advance.
  • World holds all of the state that Step() can change. It is a plain struct of values with no pointers, so a copy is a full snapshot of the game.
  • App in src/app.cpp is the program around the simulation. It measures time, reads keys, decides how many times to call Step(), and draws.

Every stage changes how App calls Step(). No stage changes how Step() uses the time it gets.

The final loop. Stages 1 to 6 each add one part of the middle box or the drawing.

The base game

Before the loop work starts, eight commits build a small platformer to test it with. The game copies the layout and conventions of the breakout template: CMake 3.24, C++20, Google clang-format style, a flat src/ folder, a core static library that the game and the tests both link, and Linux CI.

  • Level. kLevelMap in src/level.h is a text grid of 30 × 22 tiles of 32 px. The block in the bottom-left corner is exactly 3 tiles (96 px) tall. It is a ruler for the jump height.
  • Player. The player runs at 260 px/s, falls with a gravity of 2000 px/s², and jumps at 660 px/s. Collision moves the box the full distance, then pushes it out of solid tiles.
  • Jump feel. Coyote time and a jump buffer give a 0.1 s grace window on each side of a ledge.
  • Coins. One coin moves to a random spawn point when the player collects it. The world owns its own xorshift32 generator, so the seed alone decides where coins appear.
  • Debug sidebar. A panel to the right of the level shows FPS, frame time, a frame time graph, the last jump height and the number of falls out of the level.
  • Frame rate tools. Keys 1–5 cap the frame rate. H freezes one frame for 250 ms. J adds random short freezes.
Stage 1stage-1-variable-timestep

The variable timestep

Each frame measures the time since the last frame and passes it to Step() as dt. Each speed is multiplied by dt, so the player runs the same distance each second at any frame rate. Shardfield uses this loop.

const double now = GetTime();
const float dt = static_cast<float>(now - last_frame_start_);
last_frame_start_ = now;
Step(world_, level_, ReadInput(), dt);

The loop looks correct, but the size of each step now changes from frame to frame. That causes three problems.

Problem 1: the jump height depends on the frame rate

Step() changes the velocity first, then moves the player by the new velocity. This is semi-implicit Euler integration. It assumes that the velocity stays the same for the full step, so each step has an error, and a bigger step has a bigger error.

Heights measured by the game's own code. At 15 FPS the player cannot get onto the block. The exact height, v² / 2g, is never reached.

Problem 2: tunneling

Collision looks only at where the box ends up, not at the path between. H makes the next frame pass dt = 0.25. Gravity adds 500 px/s, and the player moves 125 px in one step. The floor is 32 px thick, so the box goes from above the floor to below it and never overlaps it.

Problem 3: no two runs are the same

The frame times come from the computer, not from the game. The same key presses give a slightly different game each time. Stage 5 shows why that matters.

Stage 2stage-2-fixed-step-per-frame

A fixed step per frame

The second loop mode ignores the frame time. Each frame calls Step() one time with dt = kTickSeconds (1/60 s). One call with this fixed dt is a tick. The M key, added here, changes the loop mode while the game runs.

FixesThe jump is 103.4 px at every frame rate. Tunneling is gone: at 900 px/s the player falls 15 px per tick, less than a 32 px tile. Three static_assert lines in src/world.cpp fail the build if a tuning change breaks that rule.
BreaksThe game runs at the speed of the frames. At 15 FPS a quarter of a second of game time passes each real second. At 144 FPS the game runs 2.4 times too fast. The sidebar now shows "game speed".

Old consoles used this loop, because the console and the TV ran at one fixed rate. European TVs ran at 50 Hz, so those games ran about 17% slower in Europe.

Commit: e753123 feat: step the simulation by a fixed tick once per frame.
Code to read: App::Update(), kTickSeconds in src/tuning.h, the static_assert lines in src/world.cpp.
Stage 3stage-3-accumulator

The accumulator

Stage 1 gets the speed right and the physics wrong. Stage 2 gets the physics right and the speed wrong. The accumulator gets both right. This is the loop from Glenn Fiedler's article "Fix Your Timestep!".

FixedStepClock adds each frame's real length to an accumulator, then takes out whole ticks. Time too short for a full tick stays for the next frame. A fast frame can run 0 ticks and a slow frame can run several, but over a second there are always 60.

int FixedStepClock::Advance(double frame_seconds) {
  accumulator_ += frame_seconds;
  int ticks = 0;
  while (accumulator_ >= tick_seconds_ && ticks < max_ticks_per_frame_) {
    accumulator_ -= tick_seconds_;
    ++ticks;
  }
  // ... drop any time beyond the cap (see below)
  return ticks;
}

This stage has four commits: one adds the clock, and the next three show two problems and their fixes.

Problem 1: the spiral of death

If one tick takes longer to run than the 16.7 ms it simulates, a slow frame owes more ticks, which makes the next frame slower, which owes even more. K makes each tick take 25 ms to show this. The fix is kMaxTicksPerFrame (8): the clock runs at most 8 ticks per frame and drops the rest of the time. The game then runs slower than real time, but it does not freeze.

Ticks per frame when each tick costs 25 ms, from the same model as TestSlowTicksStayAtTheLimit(). Without the cap, frame 14 takes about 4 s.

Problem 2: lost jump presses

raylib reports a key press on one frame only. At 144 FPS more than half of the frames run no tick, so more than half of the jump presses are lost. A slow frame runs several ticks, and each sees the same press. InputLatch in src/input.h keeps each press until exactly one tick takes it. Held keys follow the latest frame.

Warning: At stage-3-accumulator~3, K freezes the game in the accumulator mode. Stop the program from CLion or the terminal. At stage-3-accumulator~2, jump presses at high frame rates often do nothing.

Stage 4stage-4-interpolation

Interpolation

The accumulator makes the simulation correct, but the drawing can look uneven. A frame with no tick draws the player in the same place as the frame before. The next frame moves the player a full tick. The motion steps instead of slides. This is judder.

After the last tick of a frame, real time is a little ahead of that tick. FixedStepClock::Alpha() gives the extra time as a fraction of a tick. App keeps a copy of the world from before the last tick in previous_world_, and draws the player between the two copies by alpha.

The drawing is up to one tick (16.7 ms) late, but it moves smoothly at any frame rate.

Teleports. A respawn moves the player across the level in one tick. A line between the two places would show the player fly across the screen. LerpPlayerPosition() sees that falls changed and draws the new place at once.

Tools to see it. S turns on slow motion (6 ticks per second). G draws outlines at the last two ticks. In mode 3 the player jumps from outline to outline. In mode 4 it slides between them.

Commits: 81fcee8 interpolation, a9a41ed slow motion and tick ghosts.
Code to read: App::RunStep(), App::DrawnPlayerPosition(), LerpPlayerPosition(), FixedStepClock::Alpha().
Stage 5stage-5-replays

Deterministic replays

With a fixed tick, Step() is deterministic: the same start and the same inputs give the same world, bit for bit. A replay uses that. It holds only three things:

  1. The seed of the world's random number generator.
  2. The Input of every tick. Ten minutes of play is 36,000 small values.
  3. A hash of the world after the last tick.

HashWorld() runs FNV-1a over the exact bits of every field of World. A change of one bit in one float gives a different hash. R starts a new world from a seed and records. R again plays the inputs back from the same seed and compares the hashes. The sidebar shows MATCH or DESYNC.

What determinism needs

NeedHow Ticker meets it
A fixed dtEvery tick uses kTickSeconds. In variable timestep mode a replay gives DESYNC.
The input of each tick, not each frameApp::RunStep() records the input after the InputLatch.
Randomness inside the worldWorld::random changes only in Step(). The stutter has a separate generator.
A random generator with a known outputRandom is xorshift32. Standard library distributions can differ between compilers.
The same floating-point mathsThe same build on the same computer is exact. Across computers, games use fixed-point maths or strict compiler settings.

TestFixedTicksIgnoreFrameRate() runs the same 600 ticks at 15, 60 and 144 FPS and gets the same hash. TestVariableTimestepDependsOnFrameRate() shows the opposite.

Stage 6stage-6-time-controls

Time controls

Pause, one tick at a time, slow motion and fast forward all follow one rule:

Scale the time that goes into the accumulator. Never scale dt.

App::Frame() multiplies the real frame time by App::TimeScale() before the clock sees it. Every tick still has the same dt, so the physics does not change and replays still match.

KeyScaleEffect
P0No time goes into the accumulator, so the frame after the pause does not run a burst of ticks.
N—While paused, runs exactly one tick. Keys pressed while paused wait in the latch for it.
S0.1Slow motion: one tick for every ten frames at 60 FPS.
F (hold)4Fast forward: 4 ticks per frame at 60 FPS. At 15 FPS it needs 16, so the tick cap limits it to about x2.

The variable timestep mode can only scale dt, so there slow motion makes the jump higher and fast forward makes it lower.

Commits: d5e92f3 pause and single tick step, 02ce009 fast forward.
Code to read: App::TimeScale(), App::Update(), App::HandleFrameKeys().

The final App::Frame() does these things in order:

  1. Measure the real time since the last frame.
  2. Multiply it by the time scale.
  3. Add it to the accumulator, and take out whole ticks, up to the cap of 8.
  4. Run one Step() with a fixed dt for each tick, with input from the latch.
  5. Draw the world between the last two ticks, by alpha.

Notes on the build

  • History rewrites. No commit was pushed, so two changes went into every commit instead of a new commit at the end. A clangd cache folder (.cache/) had gone into the first commits by mistake. It is now gone and in .gitignore. Scoped enum values have no k prefix (LoopMode::Variable), because the enum name already scopes them. Plain constants keep the prefix (kTickSeconds).
  • Verification. Every commit was built from a clean checkout, and the tests ran at every commit after the first test commit. The game window was checked with screenshots. The keyboard controls were not played by hand.
  • Local build. CMake fetches raylib 5.5 from GitHub. For an offline build, point FETCHCONTENT_SOURCE_DIR_RAYLIB at a copy that is already on disk.
  • CI. The GitHub Actions workflow builds and runs the tests on Linux for pushes to main. The repository is github.com/gordysc/ticker.
